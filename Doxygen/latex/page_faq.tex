\hypertarget{page_faq_faq_errors}{}\doxysection{\texorpdfstring{runtime errors}{runtime errors}}\label{page_faq_faq_errors}
When PB3D or POST stops on an error, it prints the error message, the trace of the calling routines and the line {\ttfamily ERROR CODE \+[code]}. It then ends with an exit status that is not zero, so that a script or a batch system sees that the run failed. The exit status is the number that the shell receives when the program ends ({\ttfamily \$?} in bash). It is the error code if that lies between 1 and 125, and 1 for every other code. After a complete run and after {\ttfamily --help}, the exit status is 0; after a call with too few arguments, which prints the usage message, it is 2. Under {\ttfamily mpirun}, the launcher returns the same status.

"{}\+Cannot open input file "{}\+[name]"{}"{} &The input file, the first argument on the command line, does not exist or cannot be read. There is no default input file: the file is needed also when it sets no variable (see \doxysectlink{page_inputs}{Input variables}{0}). PB3D and POST keep only the first 120 characters of every command-\/line argument, so a long absolute path gives this error as well, and for the second file the error "{}\+No equilibrium file found."{} or "{}\+No PB3\+D file found."{}; run the program in the folder of the files and give their names relative to it. \\
"{}\+Cannot read user-\/provided file"{} &The input file contains a variable that is not part of the Fortran namelist {\ttfamily inputdata\+\_\+\+PB3D} or {\ttfamily inputdata\+\_\+\+POST}, or a value of the wrong type. The message that follows comes from the Fortran run-\/time library and usually names the variable. Check the spelling against \doxysectlink{page_inputs}{Input variables}{0}. An input that PB3D does not read, such as {\ttfamily norm\+\_\+disc\+\_\+style\+\_\+sol}, also gives this error. A file that does not contain the namelist at all gives it too, with the message "{}\+End of file"{}. \\
"{}\+BC\+\_\+style(1) has to be 1:\+ the perturbation is set to zero at the inner end"{} or "{}\+BC\+\_\+style(2) has to be 1 (fixed boundary) or 2 (free boundary with vacuum)"{} &{\ttfamily BC\+\_\+style} accepts only these values: {\ttfamily BC\+\_\+style(1) = 1} deep in the plasma, and {\ttfamily BC\+\_\+style(2) = 1} (fixed boundary) or {\ttfamily BC\+\_\+style(2) = 2} (free boundary, the default) at the plasma edge (see \doxysectlink{page_inputs}{Input variables}{0}). \\
"{}\+Free-\/boundary 3-\/\+D runs need alpha\+\_\+style 2 (multiple field lines):\+ the vacuum BEM requires n\+\_\+alpha $>$ 1"{} &For a VMEC equilibrium with a free boundary, the vacuum response is calculated with a 3-\/D boundary-\/element method on the field lines, which needs several field lines. Use {\ttfamily alpha\+\_\+style = 2} (the default for VMEC) with {\ttfamily n\+\_\+alpha} larger than 1. The related messages "{}3-\/\+D vacuum needs at least 2 field lines (n\+\_\+alpha $>$ 1)"{} and "{}3-\/\+D vacuum needs at least 4 points per field line"{} ask for a larger {\ttfamily n\+\_\+alpha} and a larger {\ttfamily min\+\_\+n\+\_\+par\+\_\+X}, respectively. \\
"{}\+The memory limit is too low, need more than N MB"{} &The equilibrium jobs (see \doxysectlink{page_overview_overview_jobs}{Equilibrium \& Perturbation Jobs}{1}) cannot be made small enough to fit in the memory limit {\ttfamily max\+\_\+tot\+\_\+mem}. Increase {\ttfamily max\+\_\+tot\+\_\+mem}. For HELENA, there is always a single equilibrium job, so the whole calculation has to fit in this limit. \\
"{}\+The memory limit is too low, the solution driver needs more than N MB"{} &The solution driver holds the integrated perturbation quantities twice, and for a free boundary the vacuum matrices, whose size grows with the square of the number of points on the plasma boundary ({\ttfamily n\+\_\+alpha} times {\ttfamily min\+\_\+n\+\_\+par\+\_\+X} for VMEC). This part cannot be divided into jobs. The number N includes the memory that every process holds of its own, about 0.\+3 GB per process on Linux, so it grows with the number of processes. Increase {\ttfamily max\+\_\+tot\+\_\+mem} to at least N. \\
"{}\+On mac\+OS, run PB3\+D with Malloc\+Large\+Cache=0 in the environment"{} &From mac\+OS 26 on, the memory allocator keeps freed blocks of memory in the program, and the system takes them back only once it is already paging memory out. PB3D then takes about twice {\ttfamily max\+\_\+tot\+\_\+mem}. Run PB3D and POST as {\ttfamily Malloc\+Large\+Cache=0 ./\+\+PB3D ...}; the variable has to be set when the program starts. \\
"{}\+The N normal points cannot be divided between P processes"{} &A grid is divided between the MPI processes in the normal direction, and every process has to keep at least one point of its own. This message from trim\+\_\+grid() means that a grid holds fewer normal points than there are processes. It usually concerns the equilibrium grid: the range between {\ttfamily min\+\_\+r\+\_\+sol} and {\ttfamily max\+\_\+r\+\_\+sol} then contains only N flux surfaces of the equilibrium file. Use at most N processes, or enlarge the normal range. \\
"{}\+The output is from PB3\+D version \+[version]\+:\+ need at least version \+[version]\+"{} &POST, and PB3D when it continues from an earlier run ({\ttfamily rich\+\_\+restart\+\_\+lvl} larger than 1), only read HDF5 output written by a PB3D version at least as recent as {\ttfamily min\+\_\+\+PB3\+D\+\_\+version} in \doxylink{namespacenum__vars}{num\+\_\+vars}. Run PB3D again with the current version. \\
"{}\+Asking to integrate with N points. Need at least 2"{} &The routine calc\+\_\+int() integrates with the trapezoidal rule, which needs at least 2 points. The message means that an integral was requested over a single point. The trace of the error message shows which routine asked for the integral. It might be that the number of points in a grid is lower than you expect because the grid is divided over the MPI processes or the equilibrium jobs; in this case, increase the number of points, use fewer processes, or allow more memory (see {\ttfamily max\+\_\+tot\+\_\+mem} in \doxysectlink{page_inputs}{Input variables}{0}). \\
"{}\+No mode is kept between normal points \+[k-\/1]\+ and \+[k]\+:\+ increase n\+\_\+mod\+\_\+\+X or refine the grid"{} &This message comes from setup\+\_\+modes(). For {\ttfamily X\+\_\+style} 2, the window of {\ttfamily n\+\_\+mod\+\_\+X} secondary mode numbers follows the most resonant values, $m = nq$ or $n = \iota m$, along the normal coordinate (see \doxysectlink{page_inputs}{Input variables}{0}). On the grid of the message, the window moves by more than its full width between two neighbouring normal points, so that these two points have no mode in common. Increase {\ttfamily n\+\_\+mod\+\_\+X}, or use a finer grid. The trace of the error message shows which grid it is: if it comes from the solution driver, it is the solution grid, set by {\ttfamily min\+\_\+r\+\_\+sol}, {\ttfamily max\+\_\+r\+\_\+sol} and {\ttfamily n\+\_\+r\+\_\+sol}, and if it comes from the perturbation driver, it is the perturbation grid, set by {\ttfamily X\+\_\+grid\+\_\+style}. \\
"{}\+EPS couldn\textquotesingle{}t find a solution. Maybe you should increase the number of parallel points."{} with error code 92, after PETSc printed "{}\+Could not locate a solver type for factorization type LU and matrix type mpibaij"{} &This happens with more than one MPI process. The eigenvalue solver uses shift-\/and-\/invert, which needs a direct LU factorization of a distributed matrix, and the built-\/in LU of PETSc only works on one process. Build PETSc with MUMPS (for example with the configure options {\ttfamily --download-\/mumps --download-\/parmetis --download-\/metis}); PETSc then uses MUMPS by itself. Alternatively, run on a single process. \\
"{}\+Zero pivot in LU factorization"{} &This message comes from PETSc. There exist cases in which the eigenvalue solver fails when {\ttfamily n\+\_\+mod\+\_\+X = 1}, for unknown reasons. Increase {\ttfamily n\+\_\+mod\+\_\+X} or play with other parameters, such as {\ttfamily norm\+\_\+disc\+\_\+prec\+\_\+sol}. \\
{\ttfamily jump\+\_\+to\+\_\+sol} does not work&Jumping over the equilibrium and perturbation drivers straight to the solution only works if the magnetic integrals of the Richardson level {\ttfamily rich\+\_\+restart\+\_\+lvl} are present in the HDF5 output, and if only solution parameters, such as the boundary conditions, are changed. With {\ttfamily X\+\_\+grid\+\_\+style = 2}, the solution grid is the perturbation grid, so the number of points in the solution, {\ttfamily n\+\_\+r\+\_\+sol}, cannot be changed, as in this case the equilibrium and perturbation drivers need to be recalculated. With {\ttfamily X\+\_\+grid\+\_\+style} 1 or 3, the solution grid is set up again from {\ttfamily n\+\_\+r\+\_\+sol}, {\ttfamily min\+\_\+r\+\_\+sol} and {\ttfamily max\+\_\+r\+\_\+sol}, and the magnetic integrals are interpolated in it (see \doxysectlink{page_overview_detail_PB3D}{Detailed PB3D Flowchart}{1}). New input values only take effect when jumping at {\ttfamily rich\+\_\+restart\+\_\+lvl = 1}, because PB3D then writes the input variables to the HDF5 output again; at a higher level, PB3D takes them from the HDF5 output of the earlier run (see the last entry in \doxysectlink{page_faq_faq_problems}{common problems}{1}). \\
The solution suffers from numerical oscillations&Change the limits of the solution grid {\ttfamily min\+\_\+r\+\_\+sol} (and possibly {\ttfamily max\+\_\+r\+\_\+sol}). The radial derivative in the solution is a left finite difference over the point itself and the {\ttfamily norm\+\_\+disc\+\_\+prec\+\_\+sol} points to its left (see set\+\_\+bc()). \\

\begin{DoxyTable}{2}{Table 2. common problems}{page_faq_faq_problems_tab}{1}
\SetCell{bg=\tableheadbgcolor,font=\bfseries}problem &\SetCell{bg=\tableheadbgcolor,font=\bfseries}solution \\
code compilation stuck&Especially with the Intel compiler, it has been found that sometimes the compiler seems to be stuck, especially for {\ttfamily \doxylink{namespaceeq__ops}{eq\+\_\+ops}}. A solution is to use less optimization through {\ttfamily -\/O2}, for example with the CMake build type {\ttfamily Rel\+With\+Deb\+Info}, which uses {\ttfamily -\/O2} for all files. \\
{\ttfamily cmake --build} does not start compiling&With CMake 3.\+31 and the Fortran headers of PETSc 3.\+25, the dependency scan of CMake loops on {\ttfamily petscmath.\+h} and {\ttfamily petscsys.\+h}, which include each other, for a long time and with a large amount of memory. CMake 4.\+3 and 4.\+4 scan the source tree without this problem. \\
A Debug build with gfortran 14 has no bounds checking&gfortran 14.\+2 and 14.\+3 miscompile the bounds check of some array subscripts in PB3D. For gfortran 14, CMake therefore builds the Debug configuration with {\ttfamily -\/fcheck=all,no-\/bounds} instead of {\ttfamily -\/fcheck=all}, and prints a message about it. Use another gfortran version to build with bounds checking. \\
{\ttfamily mpirun} crashes on mac\+OS&With the Open\+MPI 5 of Homebrew, {\ttfamily mpirun} itself can crash while it detects the hardware topology. A single-\/process run works by starting the executable directly, without {\ttfamily mpirun}, for example {\ttfamily ./\+\+PB3D PB3\+D.\+input wout.\+nc}. \\
safety factor with an extremum&The safety factor may have one or more extrema inside the normal range (reversed magnetic shear). For {\ttfamily X\+\_\+style} 2, the window of {\ttfamily n\+\_\+mod\+\_\+X} secondary mode numbers then moves up and down along the normal coordinate, and a mode can be in the window on more than one normal range. A mode can also have more than one resonant flux surface, or none: PB3D and POST print one line "{}\+Mode (n,m) = ... resonates in plasma at normalized flux surface ..."{} per resonant flux surface (see calc\+\_\+res\+\_\+surf()), and "{}does not resonate in plasma"{} for a mode without one. Close to an extremum, where $nq$ or $\iota m$ comes close to an integer without reaching it, a mode is nearly resonant over a wide normal range; check the convergence in {\ttfamily n\+\_\+r\+\_\+sol} there. \\
unphysical eigenvector&For coarse equilibrium grids and/\+or strongly varying safety factors, and when using the fast version (i.\+e. with {\ttfamily n\+\_\+mod\+\_\+X}), it is possible that the resonating mode number range varies too quickly, leading to inaccurate interpolation of tensorial perturbation quantities in the solution grid. Try using {\ttfamily X\+\_\+grid\+\_\+style} 3, where enrichment of the equilibrium grid is used to set up the perturbation grid. If this does not help, additionally lower {\ttfamily max\+\_\+njq\+\_\+change} from its default value. \\
checking convergence&Richardson extrapolation ({\ttfamily max\+\_\+it\+\_\+rich} larger than 1) checks the convergence in the number of parallel points. For {\ttfamily X\+\_\+style} 2, the window of mode numbers follows the resonant mode numbers across the plasma, and the coupling between a mode number that leaves the window and one that enters it is not kept; double {\ttfamily n\+\_\+mod\+\_\+X} once to check the result. For a free boundary with VMEC, the 3-\/D vacuum also has to converge in the number of field lines: the changelog in the code\textquotesingle{}s {\ttfamily README.\+md} records, as a rule, at least 128 field lines and about 36 parallel points per poloidal wavelength. A fixed-\/boundary run ({\ttfamily BC\+\_\+style(2) = 1}) does not calculate the vacuum. \\
low accuracy for energy reconstruction&Energy reconstruction tries to see whether by calculating the total volume integral of the perturbed potential energy and dividing it by the total volume integral of the kinetic energy of the perturbation, the eigenvalue can be recovered. This gives a lot of insight in the processes that drive the instabilities, by looking at the individual terms of these integrals, and is a good check on the internal consistency of the PB3D code. For a free boundary, the potential energy includes the vacuum term (see \doxysectlink{page_outputs_output_file_E_rec}{Energy reconstruction file}{2} in \doxysectlink{page_outputs}{Code outputs}{0}). Note that for axisymmetric equilibria, the volume integral reduces to a surface integral in a poloidal cross-\/section. It is actually very hard to perform a good energy reconstruction because the techniques used differ from the ones in the PB3D code, where the normal derivatives of the eigenvector are performed using finite differences, while in the energy reconstruction direct volume integrals are used. To get the best possible results, therefore, it is important to achieve full Richardson convergence in the number of parallel points (by increasing {\ttfamily max\+\_\+it\+\_\+rich} and/\+or {\ttfamily min\+\_\+n\+\_\+par\+\_\+X}), as well as convergence in the number of secondary mode harmonics (by increasing {\ttfamily n\+\_\+mod\+\_\+X}). Doing this, for axisymmetric cases, the code should return quite accurate results. These can furthermore be improved by choosing a finer post-\/processing grid (see {\ttfamily n\+\_\+theta\+\_\+plot} and {\ttfamily n\+\_\+zeta\+\_\+plot}). It is, however, possible that a small fraction, possibly of the order of a percent remains in the relative difference. This is probably due to the fact that in PB3D for {\ttfamily X\+\_\+style} 2 (fast), the stencil is cut when the normal index falls out of its mode range (see insert\+\_\+block\+\_\+mat()). \\
Changing input does not work for Richardson extrapolation&You cannot change the inputs as Richardson extrapolation depends on having these constant (with the exception of the number of points in the parallel integrals, but this is done internally in PB3D). When PB3D continues from an earlier run ({\ttfamily rich\+\_\+restart\+\_\+lvl} larger than 1), it reads the input variables that the run with {\ttfamily rich\+\_\+restart\+\_\+lvl = 1} wrote to the {\ttfamily in} group of the HDF5 output (see init\+\_\+rich() and reconstruct\+\_\+pb3d\+\_\+in()). These include the solution grid ({\ttfamily n\+\_\+r\+\_\+sol}, {\ttfamily min\+\_\+r\+\_\+sol}, {\ttfamily max\+\_\+r\+\_\+sol}), {\ttfamily BC\+\_\+style}, {\ttfamily norm\+\_\+disc\+\_\+prec\+\_\+sol}, the mode numbers and the field lines, so different values for these in the input file have no effect. Inputs that are not stored there, such as {\ttfamily max\+\_\+it\+\_\+rich}, {\ttfamily tol\+\_\+rich} and {\ttfamily tol\+\_\+\+SLEPC}, can be changed. \\
\end{DoxyTable}

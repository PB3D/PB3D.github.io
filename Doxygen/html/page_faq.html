runtime errors

When PB3D or POST stops on an error, it prints the error message, the trace of the calling routines and the line ERROR CODE [code]. It then ends with an exit status that is not zero, so that a script or a batch system sees that the run failed. The exit status is the number that the shell receives when the program ends ($? in bash). It is the error code if that lies between 1 and 125, and 1 for every other code. After a complete run and after –help, the exit status is 0; after a call with too few arguments, which prints the usage message, it is 2. Under mpirun, the launcher returns the same status.

Table 1. frequently encountered errors
error solution
"Cannot open input file "[name]"" The input file, the first argument on the command line, does not exist or cannot be read. There is no default input file: the file is needed also when it sets no variable (see Input variables). PB3D and POST keep only the first 120 characters of every command-line argument, so a long absolute path gives this error as well, and for the second file the error "No equilibrium file found." or "No PB3D file found."; run the program in the folder of the files and give their names relative to it.
"Cannot read user-provided file" The input file contains a variable that is not part of the Fortran namelist inputdata_PB3D or inputdata_POST, or a value of the wrong type. The message that follows comes from the Fortran run-time library and usually names the variable. Check the spelling against Input variables. An input that PB3D does not read, such as norm_disc_style_sol, also gives this error. A file that does not contain the namelist at all gives it too, with the message "End of file".
"BC_style(1) has to be 1: the perturbation is set to zero at the inner end" or "BC_style(2) has to be 1 (fixed boundary) or 2 (free boundary with vacuum)" BC_style accepts only these values: BC_style(1) = 1 deep in the plasma, and BC_style(2) = 1 (fixed boundary) or BC_style(2) = 2 (free boundary, the default) at the plasma edge (see Input variables).
"Free-boundary 3-D runs need alpha_style 2 (multiple field lines): the vacuum BEM requires n_alpha > 1" For a VMEC equilibrium with a free boundary, the vacuum response is calculated with a 3-D boundary-element method on the field lines, which needs several field lines. Use alpha_style = 2 (the default for VMEC) with n_alpha larger than 1. The related messages "3-D vacuum needs at least 2 field lines (n_alpha > 1)" and "3-D vacuum needs at least 4 points per field line" ask for a larger n_alpha and a larger min_n_par_X, respectively.
"The memory limit is too low, need more than N MB" The equilibrium jobs (see Equilibrium & Perturbation Jobs) cannot be made small enough to fit in the memory limit max_tot_mem. Increase max_tot_mem. For HELENA, there is always a single equilibrium job, so the whole calculation has to fit in this limit.
"The N normal points cannot be divided between P processes" A grid is divided between the MPI processes in the normal direction, and every process has to keep at least one point of its own. This message from trim_grid() means that a grid holds fewer normal points than there are processes. It usually concerns the equilibrium grid: the range between min_r_sol and max_r_sol then contains only N flux surfaces of the equilibrium file. Use at most N processes, or enlarge the normal range.
"The output is from PB3D version [version]: need at least version [version]" POST, and PB3D when it continues from an earlier run (rich_restart_lvl larger than 1), only read HDF5 output written by a PB3D version at least as recent as min_PB3D_version in num_vars. Run PB3D again with the current version.
"Asking to integrate with N points. Need at least 2" The routine calc_int() integrates with the trapezoidal rule, which needs at least 2 points. The message means that an integral was requested over a single point. The trace of the error message shows which routine asked for the integral. It might be that the number of points in a grid is lower than you expect because the grid is divided over the MPI processes or the equilibrium jobs; in this case, increase the number of points, use fewer processes, or allow more memory (see max_tot_mem in Input variables).
"No mode is kept between normal points [k-1] and [k]: increase n_mod_X or refine the grid" This message comes from setup_modes(). For X_style 2, the window of n_mod_X secondary mode numbers follows the most resonant values, \(m = nq\) or \(n = \iota m\), along the normal coordinate (see Input variables). On the grid of the message, the window moves by more than its full width between two neighbouring normal points, so that these two points have no mode in common. Increase n_mod_X, or use a finer grid. The trace of the error message shows which grid it is: if it comes from the solution driver, it is the solution grid, set by min_r_sol, max_r_sol and n_r_sol, and if it comes from the perturbation driver, it is the perturbation grid, set by X_grid_style.
"EPS couldn't find a solution. Maybe you should increase the number of parallel points." with error code 92, after PETSc printed "Could not locate a solver type for factorization type LU and matrix type mpibaij" This happens with more than one MPI process. The eigenvalue solver uses shift-and-invert, which needs a direct LU factorization of a distributed matrix, and the built-in LU of PETSc only works on one process. Build PETSc with MUMPS (for example with the configure options –download-mumps –download-parmetis –download-metis); PETSc then uses MUMPS by itself. Alternatively, run on a single process.
"Zero pivot in LU factorization" This message comes from PETSc. There exist cases in which the eigenvalue solver fails when n_mod_X = 1, for unknown reasons. Increase n_mod_X or play with other parameters, such as norm_disc_prec_sol.
jump_to_sol does not workJumping over the equilibrium and perturbation drivers straight to the solution only works if the magnetic integrals of the Richardson level rich_restart_lvl are present in the HDF5 output, and if only solution parameters, such as the boundary conditions, are changed. With X_grid_style = 2, the solution grid is the perturbation grid, so the number of points in the solution, n_r_sol, cannot be changed, as in this case the equilibrium and perturbation drivers need to be recalculated. With X_grid_style 1 or 3, the solution grid is set up again from n_r_sol, min_r_sol and max_r_sol, and the magnetic integrals are interpolated in it (see Detailed PB3D Flowchart). New input values only take effect when jumping at rich_restart_lvl = 1, because PB3D then writes the input variables to the HDF5 output again; at a higher level, PB3D takes them from the HDF5 output of the earlier run (see the last entry in common problems).
The solution suffers from numerical oscillationsChange the limits of the solution grid min_r_sol (and possibly max_r_sol). The radial derivative in the solution is a left finite difference over the point itself and the norm_disc_prec_sol points to its left (see set_bc()).

common problems

Table 2. common problems
problem solution
code compilation stuckEspecially with the Intel compiler, it has been found that sometimes the compiler seems to be stuck, especially for eq_ops. A solution is to use less optimization through -O2, for example with the CMake build type RelWithDebInfo, which uses -O2 for all files.
cmake –build does not start compilingWith CMake 3.31 and the Fortran headers of PETSc 3.25, the dependency scan of CMake loops on petscmath.h and petscsys.h, which include each other, for a long time and with a large amount of memory. CMake 4.3 and 4.4 scan the source tree without this problem.
A Debug build with gfortran 14 has no bounds checkinggfortran 14.2 and 14.3 miscompile the bounds check of some array subscripts in PB3D. For gfortran 14, CMake therefore builds the Debug configuration with -fcheck=all,no-bounds instead of -fcheck=all, and prints a message about it. Use another gfortran version to build with bounds checking.
mpirun crashes on macOSWith the OpenMPI 5 of Homebrew, mpirun itself can crash while it detects the hardware topology. A single-process run works by starting the executable directly, without mpirun, for example ./PB3D PB3D.input wout.nc.
safety factor with an extremumThe safety factor may have one or more extrema inside the normal range (reversed magnetic shear). For X_style 2, the window of n_mod_X secondary mode numbers then moves up and down along the normal coordinate, and a mode can be in the window on more than one normal range. A mode can also have more than one resonant flux surface, or none: PB3D and POST print one line "Mode (n,m) = ... resonates in plasma at normalized flux surface ..." per resonant flux surface (see calc_res_surf()), and "does not resonate in plasma" for a mode without one. Close to an extremum, where \(nq\) or \(\iota m\) comes close to an integer without reaching it, a mode is nearly resonant over a wide normal range; check the convergence in n_r_sol there.
unphysical eigenvectorFor coarse equilibrium grids and/or strongly varying safety factors, and when using the fast version (i.e. with n_mod_X), it is possible that the resonating mode number range varies too quickly, leading to inaccurate interpolation of tensorial perturbation quantities in the solution grid. Try using X_grid_style 3, where enrichment of the equilibrium grid is used to set up the perturbation grid. If this does not help, additionally lower max_njq_change from its default value.
checking convergenceRichardson extrapolation (max_it_rich larger than 1) checks the convergence in the number of parallel points. For X_style 2, the window of mode numbers follows the resonant mode numbers across the plasma, and the coupling between a mode number that leaves the window and one that enters it is not kept; double n_mod_X once to check the result. For a free boundary with VMEC, the 3-D vacuum also has to converge in the number of field lines: the changelog in the code's README.md records, as a rule, at least 128 field lines and about 36 parallel points per poloidal wavelength. A fixed-boundary run (BC_style(2) = 1) does not calculate the vacuum.
low accuracy for energy reconstructionEnergy reconstruction tries to see whether by calculating the total volume integral of the perturbed potential energy and dividing it by the total volume integral of the kinetic energy of the perturbation, the eigenvalue can be recovered. This gives a lot of insight in the processes that drive the instabilities, by looking at the individual terms of these integrals, and is a good check on the internal consistency of the PB3D code. For a free boundary, the potential energy includes the vacuum term (see Energy reconstruction file in Code outputs). Note that for axisymmetric equilibria, the volume integral reduces to a surface integral in a poloidal cross-section. It is actually very hard to perform a good energy reconstruction because the techniques used differ from the ones in the PB3D code, where the normal derivatives of the eigenvector are performed using finite differences, while in the energy reconstruction direct volume integrals are used. To get the best possible results, therefore, it is important to achieve full Richardson convergence in the number of parallel points (by increasing max_it_rich and/or min_n_par_X), as well as convergence in the number of secondary mode harmonics (by increasing n_mod_X). Doing this, for axisymmetric cases, the code should return quite accurate results. These can furthermore be improved by choosing a finer post-processing grid (see n_theta_plot and n_zeta_plot). It is, however, possible that a small fraction, possibly of the order of a percent remains in the relative difference. This is probably due to the fact that in PB3D for X_style 2 (fast), the stencil is cut when the normal index falls out of its mode range (see insert_block_mat()).
Changing input does not work for Richardson extrapolationYou cannot change the inputs as Richardson extrapolation depends on having these constant (with the exception of the number of points in the parallel integrals, but this is done internally in PB3D). When PB3D continues from an earlier run (rich_restart_lvl larger than 1), it reads the input variables that the run with rich_restart_lvl = 1 wrote to the in group of the HDF5 output (see init_rich() and reconstruct_pb3d_in()). These include the solution grid (n_r_sol, min_r_sol, max_r_sol), BC_style, norm_disc_prec_sol, the mode numbers and the field lines, so different values for these in the input file have no effect. Inputs that are not stored there, such as max_it_rich, tol_rich and tol_SLEPC, can be changed.
